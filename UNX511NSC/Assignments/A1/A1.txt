Part 1: Dynamic File Generation
Q1: Why do we use O_CREAT | O_TRUNC in open()?
O_CREAT creates the file if it doesn’t exist.
O_TRUNC clears the file’s contents if it does exist.
This ensures each execution starts with a fresh file instead of appending to old data.

Q2: What happens if write() fails inside the loop?
The data won’t be written to the file.
write() returns -1 and sets errno.
If we don’t check for errors, we might assume the file is valid when it’s incomplete or corrupted.

Q3: Why do we use memset() before writing to the file?
memset() fills the buffer with dummy data (like 'X') to make real binary content.
It make sure each MB written has actual bytes rather than random garbage.


Part 2: Worker Processes
Q1: Why do we check /proc/self/status for memory usage?
It’s a special file that shows real-time info about the current process.
We use it to check how much memory the worker is using (VmRSS) at any point in time.

Q2: What would happen if kill(parent_pid, SIGUSR1) fails?
If the parent PID is invalid or has exited, kill() fails and returns -1.
The signal won’t be sent, so the parent won’t be notified.
It’s important to check the return value and possibly log an error.


Q3: How does read() behave differently in blocking vs non-blocking mode?
In blocking mode (default), read() waits until data is available.
In non-blocking mode, read() returns immediately, even if there’s no data yet (returns 0 or -1).
Blocking mode is safer for large file reads like this to avoid race conditions.


Part 3: Parent Process & Signals
Q1: What happens if two workers send SIGUSR1 at the same time?
Signals are asynchronous, and they can arrive almost simultaneously.
But the OS queues and delivers them one at a time.
If we don’t track workers properly, we might print or log duplicate memory warnings.


Q2: Why is signal(SIGUSR1, xx_signal_handler); needed in main()?
Without it, the process would use the default signal behavior (which might kill the process or do nothing). Registering a handler tells the program how to respond when the signal arrives — e.g., log the event or update status.


Part 4: Secure Logging
Q1: What is F_WRLCK and why do we use it?
F_WRLCK is a write lock.
It prevents other processes from writing to the file at the same time, avoiding partial writes or corrupted logs.


Q2: How does file locking prevent data corruption?
It ensures that only one process writes to the log file at a time.
This avoids issues where multiple workers might mix their messages or overwrite each other’s logs. It’s critical in concurrent environments where many processes access shared files.
